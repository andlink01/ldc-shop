# 付款后采购：第三方取卡接口规范（v1）

适用于 Workers 和 Docker **1.5.14** 的“付款后采购”商品，两版接口与业务行为一致，Docker 需要从本仓库构建镜像。商城先确认付款，再向供应商申请卡密，取得后自动整单发货。若第三方生成需要 5～10 秒，可在同一请求内完成；超时、排队或多件采购会延长实际发货时间。

这与商城自己的 `/api/v1/products/.../cards` 补卡 API 是两个方向：本文是**商城调用供应商**。后台填写的供应商 Token 由第三方校验，“补货接口”页生成的密钥用于外部工具调用商城，见 [商城补货接口](inventory-api.md)。第三方需要自行实现和部署本文的接口，商城保存地址不会创建第三方服务。

## 对接前需要交换什么资料

**店主提供商品编码和生成要求；第三方实现取卡接口，再给店主 API 地址和供应商 Token。** 买家付款后由商城调用第三方，取得卡密再整单发货。

| 店主给第三方开发者的资料 | 要写清楚的内容 |
|---|---|
| 本文的接口规范 | 请求字段、200/202 响应及持久去重规则都必须按本文实现 |
| 商品编码与生成内容的对应关系 | 例如 `invitationcode` 对应哪类兑换码、账号或使用套餐；每个商品和规格分别列出 |
| 卡密有效期要求 | 永久有效，或生成后有效多久；有限期卡须按正文规范返回 `expiresAt`，并留出整单等待时间 |
| 预计生成耗时 | 例如 5～10 秒；无法在 20 秒内完成时先返回 202，完成后相同编号请求返回原结果 |

| 第三方给店主的资料 | 店主如何使用 |
|---|---|
| 已部署的取卡 API 地址 | 填入对应商品“卡密管理”的 API 地址；地址必须可直接接收 POST，不能只是第三方网站首页 |
| 供应商 Token，以及是否必须鉴权 | 由第三方生成并校验，填入同一页面的 API Token；第三方明确不要求鉴权时可留空 |

这里使用的是**第三方提供的供应商 Token**，无需把商城“补货接口”创建的密钥交给第三方，也不需要提供商城管理员账号、支付密钥或数据库权限。`requestId`、`orderId`、`itemIndex` 由商城在实际采购时发送，店主不需要提前生成订单号或采购编号。

可以复制以下资料模板，填写后交给第三方开发者：

```text
对接方式：买家付款后，商城向第三方采购卡密
接口规范：https://github.com/andlink01/ldc-shop/blob/main/docs/supplier-api.md
商品编码：invitationcode（替换为实际编码，每个规格单独列出）
生成内容/规格：填写该编码需要生成的卡密类型或套餐
有效期要求：填写永久有效，或生成后多久到期
预计生成耗时：填写预计秒数
每次申请数量：quantity 固定为 1；多件订单分别请求
去重要求：相同 requestId 只生成、只计费一次，重试返回保存的同一卡密
返回要求：20 秒内完成返回 200；尚未完成返回 202，后台继续生成
交付资料：可用的 POST API 地址、供应商 Token、是否要求 Token 鉴权
```

第三方交付后，店主按下面的后台步骤配置，并按文末验收步骤检查重试与发货。

## 后台配置

1. 第三方实现下面的 POST 接口、鉴权和持久去重，将商城商品编码映射到需要生成的卡密类型。
2. 在“商品管理 → 卡密管理”将发货模式设为“付款后采购”，填写第三方取卡接口地址和 Token，保存后点击“启用”。
3. 商品需要上架，并满足商城原有登录、购买验证、限购等条件。测试接口通过后再用测试商品检查付款和整单发货。

地址只包含协议、域名和路径，支持 `http` / `https`，正式接口建议 HTTPS；不允许用户名、密码、查询参数或片段。最长 1000 字符。Token 最长 1000 字符，不允许换行或 NUL，首尾空白会去掉。该模式不适用于共享卡密商品。

API 地址在启用时必须填写；Token 由第三方提供，对方不要求验证时可留空。地址和 Token 都留空时只能保存未启用配置，不能让商城凭空生成卡密。页面用“已启用／未启用”显示当前状态，用“启用／停用”按钮执行操作。

保存或启用配置不会为尚未付款的订单采购；已有已付款待发货订单会继续恢复。无需提前添加卡密，启用后商品可以下单。每单最多 100 件，分件申请，每件对应一个固定请求编号。已有有效卡密会先用于发货，缺少的部分才向供应商采购。

原有“库存补货”模式仍通过 GET 获取单条卡密：保存为启用状态或点击启用时尝试拉取一条，每个订单成功发货后再尝试补一条（不是按购买件数补齐），失败可手动拉取。该模式仍要求下单前有足够有效库存，响应格式见 [Workers README](../_workers_next/README.md#-卡密自动补货-api-对接)。

“付款后采购”不通过“手动拉取”购买无订单卡密；恢复采购请到“订单补发”点击“重试发货”。停用配置不会取消或退款已有已付款订单，执行中的采购请求也可能完成。

## 请求

接口路径由第三方自行选择，例如 `https://supplier.example.com/api/cards/issue`。商城请求：

```http
POST /api/cards/issue
Content-Type: application/json
Accept: application/json
Authorization: Bearer <后台配置的供应商 Token>
Idempotency-Key: 8ec211d9-76fc-4a47-8b56-a1d5859b26f8
```

```json
{
  "requestId": "8ec211d9-76fc-4a47-8b56-a1d5859b26f8",
  "orderId": "LDC_ORDER_EXAMPLE",
  "productId": "invitationcode",
  "quantity": 1,
  "itemIndex": 0
}
```

| 字段 | 规则 |
| --- | --- |
| `requestId` | UUID，重试、重启、重复支付回调时保持相同；与 `Idempotency-Key` 一致 |
| `orderId` | 商城订单编号 |
| `productId` | 商城商品编码；供应商用它选择需要生成的卡密类型 |
| `quantity` | 当前接口固定为 `1`，每次申请一条 |
| `itemIndex` | 同订单中的采购序号，从 `0` 开始 |

不传买家邮箱、个人信息或支付密钥。Token 未配置时不发送 Authorization 头，正式接口建议要求校验 Token。

`requestId` 是每件采购的去重标识，不要只按 `orderId` 去重，否则多件订单只能取到一条。`itemIndex` 最大为 99；已有库存可能使订单提前发货，供应商不能假定一定收到该订单的全部 100 个序号。

商城不自动追加 `productId` 到 URL，第三方从 JSON 正文读取商品编码。商城不跟随 301/302/307/308 等重定向，必须填写可直接接收 POST 的最终地址；失败重定向不会携带 Token 请求目标地址。

## 成功响应

HTTP **200**，`Content-Type: application/json`：

```json
{
  "success": true,
  "requestId": "8ec211d9-76fc-4a47-8b56-a1d5859b26f8",
  "data": {
    "cardKey": "EXAMPLE-CARD-KEY",
    "expiresAt": "2026-12-31T23:59:59Z"
  }
}
```

| 字段 | 规则 |
|---|---|
| `success` | 必须是布尔值 `true`，不能是 `"true"` 或 `1` |
| `requestId` | 必须与当前请求完全一致 |
| `data.cardKey` | 一条卡密字符串，原始长度最多 4096 字符；去掉首尾空白后不能为空，不含 NUL |
| `data.expiresAt` | 可选；带时区的 ISO 时间或 `null`，不支持相对秒数 |

响应总大小不超过 32 KiB，超过上限、无效 JSON 或缺少字段都不会入库。固定使用上述对象结构，不支持旧 GET 模式的纯文本、数组、`card` / `key` / `code` 或嵌套兼容格式。

不同采购编号必须产生不同卡密。商城按**同一商品内去掉首尾空白后的卡密文本**拒绝重复，包括已经使用或过期的历史卡密；不能靠相同编号重试更换一条新卡。首尾空白会去掉，内部换行会保留。

`expiresAt` 格式为 `YYYY-MM-DDTHH:mm:ss[.SSS]Z` 或带 `±HH:mm` 时区，小数秒可为 1–3 位，例如 `"2026-12-31T23:59:59+08:00"`；不接受 Unix 时间戳或无时区时间。永久卡可省略或填 `null`。商城验证时至少还需 60 秒有效期，建议有效期覆盖整个订单排队和多件生成过程；5 分钟是建议值，不是保证。

过期卡密不参与发货。已收到的采购若在整单凑齐前过期，商城不会给该序号换采购编号重新收费，需要管理员补入有效卡密或处理退款。供应商持久保存的原响应不能因到期而悄悄改成新卡。

规范使用 HTTP 200；当前实现也会按相同字段校验其他成功 2xx（202 除外），但空正文的 204 不能发货。

## 尚在生成

HTTP **202**：

```json
{
  "success": true,
  "requestId": "8ec211d9-76fc-4a47-8b56-a1d5859b26f8",
  "status": "processing"
}
```

商城每次请求最多等待 20 秒（包含响应读取）。生成任务来不及完成时，第三方先返回 202，在后台继续生成。202 的正文仅供第三方调试，商城不读取其中的卡密、处理进度或轮询地址，始终将它视为未完成。

商城随后以**相同 POST 请求和相同编号**重试；完成后返回之前保存的 200 结果。无需另建查询接口或向商城推送回调。商城不读取 `Retry-After` 来改变重试时间。

## 必须实现的去重规则

1. 以 `requestId` 为数据库唯一键，先原子登记“处理中”，再启动生成。不能仅靠进程内缓存或先查询后插入。
2. 相同编号和相同参数只生成一条、只计费一次。并发请求中只有一个可以开始生成，其他返回 202 或已经保存的结果。
3. 成功后持久保存完整响应。以后相同编号始终返回同一卡密，不能因为商城断开连接、超时、重启或卡密已经生成就再生成一次。
4. 相同编号的参数被改动时返回 HTTP 409，不能覆盖原结果。
5. 请求连接断开时保留生成任务和去重记录。失败重试沿用原编号；若后台已经生成成功，应直接返回成功记录。
6. 去重记录建议永久保存；若业务必须清理，至少保留 90 天且不能清理未完成订单。商城自动重试没有 90 天截止限制，记录清理前必须人工确认不会再收到原编号请求，否则不能保证只生成、只计费一次。

伪代码：

```text
验证 Token、requestId、商品与参数
原子 INSERT requestId（唯一键）、参数指纹、processing
已存在：
  参数不同 → 409
  已完成 → 返回保存的 200 JSON
  正在生成 → 202
首次创建：
  在后台生成一次卡密
  保存卡密与 complete 状态
  能在 20 秒内完成 → 200，否则先返回 202
```

401/403 表示认证或权限问题，409 表示编号冲突，429 表示限流，5xx 表示临时故障。HTTP 200 返回 `success: false` 也视为无效响应，不会取消订单。商城不会把第三方原始错误、Token 或卡密写入请求错误记录；失败订单保留“已付款”，不会自动退款。

商城在本地持久保存采购编号、租约和入库结果，返回卡密先预留给对应已付款订单；整单数量满足才发货。生成期间如果订单已退款，返回卡密保留为库存，不再向该订单发货。

## 自动重试与故障处理

采购任务和采购编号保存在商城数据库，重启和重复支付回调沿用原编号。请求结束后的后台任务会尝试处理；现有每分钟 Cron 继续扫描到期任务，每轮默认处理最多 10 个库存事件（与通知任务共用队列）。

每次自动处理同一订单最多顺序发起 3 次采购；中途遇到未完成或失败就停止该轮。首次未完成后安排约 60 秒再试，后续为 120、240、480、960 秒，再封顶 30 分钟；实际执行还受 Cron 扫描和队列影响。大订单可能分多轮采购，无法保证全部在 20 秒内完成。

401/403/409、其他 HTTP 错误、超时和无效返回也进入重试，不会自动终止采购。不能把错误状态码当作“取消采购”的协议。修复供应商服务或配置后，商城仍使用原编号请求。

后台“订单补发 → 重试发货”先尝试现有库存，仍不足时最多发起 1 次采购，不等待自动任务的下次执行时间。同一采购请求的租约为 60 秒；两版手动与后台处理共用 5 分钟的任务租约，重复点击不会接管执行中的任务或并发取卡。正常请求结束会释放租约，进程中断时可能需要等任务租约到期才能接管。

| 状态/错误编码 | 含义与处理 |
|---|---|
| `supplier_processing` | 第三方返回 202，等待原任务完成 |
| `supplier_request_in_progress` | 该采购已有执行中请求，等待租约释放 |
| `supplier_http_<状态码>` | 第三方 HTTP 失败；检查鉴权、服务状态、限流或重定向 |
| `supplier_request_failed` | 请求/读取超时、网络失败、无效 JSON、超大响应或保存失败等；排查第三方与商城运行日志 |
| `supplier_invalid_response` | 编号、字段、卡密或有效期不符合规范 |
| `supplier_duplicate_card` | 同一商品已有该卡密，或本次未能成功登记卡密；核查第三方去重结果 |
| `supplier_waiting_for_cards` | 本轮完成但整单有效数量仍不足，等待后续处理或人工补卡 |
| `supplier_disabled`、`supplier_url_invalid` | 配置停用、不符合采购模式、缺少或无效地址 |
| `supplier_endpoint_changed` | 接口地址与采购记录不同；核对原结果后在“订单补发”更新地址并重试，也可补卡或退款 |

采购请求记录与库存任务记录分别保存错误。两版手动补发和后台采购共用任务租约；手动请求结束后同步最新结果，页面不再被上一次后台错误覆盖。重试提示直接显示本次失败或处理中原因；已发货订单从补发列表移除。自动任务完成后，可点击页面“刷新”查看新状态。错误不会包含第三方原始返回；需要第三方按 `requestId` 查询其生成记录。

商品接口地址改变后，未完成采购不会自动迁移或生成新编号。两版均提供管理员处理入口：

1. 先确认原接口没有生成卡密，或新旧地址连接同一套持久去重记录。已生成的卡密应先核对，不能直接改用另一家供应商再次采购。
2. 在“订单补发”对应订单点击“更新取卡地址”，核对显示的原地址、当前商品地址与采购编号，并确认原采购结果。
3. 点击“更新地址并重试”。仅本订单未完成请求改用当前地址；采购编号、已收到卡密和其他订单保持不变，随后尝试一次手动补发，后台继续恢复剩余部分。

处理入口不会创建新的采购编号。执行中任务不能改地址；订单状态、配置或请求记录在确认期间变化时，操作会拒绝，要求刷新确认。地址更新和审计记录在同一个数据库事务中保存（Workers 为 D1 批次，Docker 为 SQLite 事务）；审计存入已有 `inventory_events`，保留原地址及请求编号，不保存供应商 Token。

如果无法确认旧接口的结果，应联系第三方按原采购编号查询，或使用已有卡密、退款处理。不要把已付款订单直接删掉作为发货解决方式。Token 可以更新，重试使用当前商品配置的 Token；仅更新 Token 无需迁移采购地址。

Cron 鉴权依次读取 `CRON_CLEANUP_TOKEN`、`OAUTH_CLIENT_SECRET`。已有 Linux DO OAuth Secret 时可沿用回退值；仅配置 GitHub 登录和 `AUTH_SECRET` 时，需额外设置独立随机 Secret `CRON_CLEANUP_TOKEN`，否则定时重试会跳过。`AUTH_SECRET` 不是 Cron 的回退值。Workers 沿用现有每分钟 Cron、Worker 入口和 D1 绑定；Docker 由容器内 `cron.mjs` 每分钟调用相同恢复路由，无需新增供应商回调。全局补发按商品轮转；完整有效的订单专属预留可以先发货，公共库存仍按付款顺序分配。

## 第三方上线前验收

在第三方测试环境对同一编号重复、并发发送上述 POST：

1. 首次生成成功返回 200；后续返回完全相同的编号、卡密和到期时间，只生成、只计费一次。
2. 将同一编号的 `productId` 或 `itemIndex` 改动，返回 409，不产生新卡。
3. 生成需要超过 20 秒时及时返回 202；重试期间返回 202，完成后返回已保存的 200。
4. 模拟商城断开连接、第三方重启后再请求相同编号，仍返回原结果。
5. 不同编号分别生成不同卡密；校验错误 Token、空卡密、到期卡和服务故障的行为。

再用隔离商城或测试商品验证零库存下单、付款、多件整单发货、超时重试和退款期间取卡，避免用生产买家的订单测试。“库存补货”的旧 GET 接口不具备本文的编号和去重协议，需第三方实现此 POST 规范后才能使用付款后采购。两版 GET 补货会按商品现存卡密记录拒绝相同内容，包括已售、过期和并发重复返回；这项商城入库检查不能代替供应商按采购编号只生成、只计费一次。
