# 付款后采购：第三方取卡接口规范（v1）

适用于 Workers 版的“付款后采购”商品。商城先确认付款，再向供应商申请卡密；供应商通常在 5～10 秒内生成，商城取得后自动整单发货。

这与商城自己的 `/api/v1/products/.../cards` 补卡 API 是两个方向：本文是**商城调用供应商**。后台填写的供应商 Token 由第三方校验，库存 API 管理页生成的密钥用于外部工具调用商城。

## 后台配置

在“商品管理 → 卡密管理 → 卡密 API 自动补货”选择“付款后采购（POST 接口）”，填写第三方完整接口地址和 Token，保存并启用。接口地址只包含协议、域名和路径，不放 Token 或其他查询参数。该模式不适用于共享卡密商品。

保存配置不采购；无需提前添加卡密，商品可以下单。每单最多 100 件，分件申请，每件对应一个固定请求编号。已有有效卡密会先用于发货，缺少的部分才向供应商采购。

原有“库存补货”模式仍通过 GET 获取单条卡密：保存并启用时尝试拉取一条，发货后再补一条。该模式仍要求下单前有足够有效库存。

## 请求

接口路径由第三方自行选择，例如 `https://supplier.example.com/api/cards/issue`。商城请求：

```http
POST /api/cards/issue
Content-Type: application/json
Accept: application/json
Authorization: Bearer <后台配置的供应商 Token>
Idempotency-Key: 8ec211d9-76fc-4a47-8b56-a1d5859b26f8
```

```json
{
  "requestId": "8ec211d9-76fc-4a47-8b56-a1d5859b26f8",
  "orderId": "LDC_ORDER_EXAMPLE",
  "productId": "invitationcode",
  "quantity": 1,
  "itemIndex": 0
}
```

| 字段 | 规则 |
| --- | --- |
| `requestId` | UUID，重试、重启、重复支付回调时保持相同；与 `Idempotency-Key` 一致 |
| `orderId` | 商城订单编号 |
| `productId` | 商城商品编码；供应商用它选择需要生成的卡密类型 |
| `quantity` | 当前接口固定为 `1`，每次申请一条 |
| `itemIndex` | 同订单中的采购序号，从 `0` 开始 |

不传买家邮箱、个人信息或支付密钥。Token 未配置时不发送 Authorization 头，正式接口建议要求校验 Token。

## 成功响应

HTTP **200**，`Content-Type: application/json`：

```json
{
  "success": true,
  "requestId": "8ec211d9-76fc-4a47-8b56-a1d5859b26f8",
  "data": {
    "cardKey": "EXAMPLE-CARD-KEY",
    "expiresAt": "2026-12-31T23:59:59Z"
  }
}
```

`cardKey` 必须是非空字符串，最长 4096 字符，不含 NUL。不同采购编号必须产生不同卡密。响应总大小不超过 32 KiB。

`expiresAt` 使用带时区的 ISO 8601 时间，永久卡可省略或填 `null`。返回时至少还有 60 秒有效期，建议不少于 5 分钟。过期或格式错误的卡密不会发给买家。

## 尚在生成

HTTP **202**：

```json
{
  "success": true,
  "requestId": "8ec211d9-76fc-4a47-8b56-a1d5859b26f8",
  "status": "processing"
}
```

商城每次最多等待 20 秒。生成任务来不及完成时，第三方先返回 202，在后台继续生成。商城随后以**相同 POST 请求和相同编号**重试；完成后返回之前保存的 200 结果。无需另建查询接口或回调接口。

## 必须实现的去重规则

1. 以 `requestId` 为数据库唯一键，先原子登记“处理中”，再启动生成。不能仅靠进程内缓存或先查询后插入。
2. 相同编号和相同参数只生成一条、只计费一次。并发请求中只有一个可以开始生成，其他返回 202 或已经保存的结果。
3. 成功后持久保存完整响应。以后相同编号始终返回同一卡密，不能因为商城断开连接、超时、重启或卡密已经生成就再生成一次。
4. 相同编号的参数被改动时返回 HTTP 409，不能覆盖原结果。
5. 请求连接断开时保留生成任务和去重记录。失败重试沿用原编号；若后台已经生成成功，应直接返回成功记录。
6. 去重记录不要短期过期；建议永久保存，至少保留 90 天，未完成订单不能清理。

伪代码：

```text
验证 Token、requestId、商品与参数
原子 INSERT requestId（唯一键）、参数指纹、processing
已存在：
  参数不同 → 409
  已完成 → 返回保存的 200 JSON
  正在生成 → 202
首次创建：
  在后台生成一次卡密
  保存卡密与 complete 状态
  能在 20 秒内完成 → 200，否则先返回 202
```

401/403 表示认证或权限问题，409 表示编号冲突，429 表示限流，5xx 表示临时故障。商城不会把第三方原始错误、Token 或卡密写入请求错误记录；失败订单保留“已付款”，在后台“异常订单补发”可查看状态、重试。

商城在本地持久保存采购编号、租约和入库结果，返回卡密先预留给对应已付款订单；整单数量满足才发货。生成期间如果订单已退款，返回卡密保留为库存，不再向该订单发货。

自动重试由请求结束后的后台任务和现有清理定时任务处理。Workers 保留原 Cron 与 D1 绑定；“卡密 API 自动补货”旧 GET 接口不具备此去重保证，不能直接用于“付款后采购”。
